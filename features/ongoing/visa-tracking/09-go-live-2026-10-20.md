## 2. Before deploying

- [ ] Backup: database and private files.
- [ ] Free memory: two OCR workers need up to about 4 GB at the same time.
      If the server has less, set `background_workers` to 1 in step 3.3.
- [ ] Note how many Passport Extractions are `Queued` or `Processing`
      (they are moved in step 5).

## 3. Deploy

1. [ ] Pull `passport_extractor` and `the_visaguy` (`main`). Confirm the
       other apps are at the heads in `08-go-live-checklist.md` section 0b.
2. [ ] `bench --site <live> migrate`. Expect the line
       "Added the 'passport_extraction' queue to common_site_config.json".
3. [ ] `sites/common_site_config.json` has
       `"passport_extraction": {"timeout": 1800, "background_workers": 2}`
       under `workers`, next to `capi`.
4. [ ] `bench setup supervisor`, then
       `sudo supervisorctl reread && sudo supervisorctl update`.
       `sudo supervisorctl status` shows the passport_extraction worker group
       with 2 processes. Compare the generated config before you accept it if
       supervisor has hand edits.
5. [ ] `bench build --app passport_extractor`, then `bench restart`.
       (The restart stops any running OCR job; step 5 restarts those.)

## 4. Configure

- [ ] Visa Tracker Settings → Queues → Extraction Queue = `passport_extraction`.
- [ ] Optional: site config `"passport_extractor_textline_orientation": 0`.
      Same results on all 36 pilot files, average 77.6 s → 46.1 s per file.
      Needs a worker restart to take effect.

## 5. Move waiting jobs

- [ ] Passport Extraction list → **Requeue Pending Extractions** (System
      Manager). Read the dry run: "Move from another queue", "Restart (no
      running job)", "Running now, left alone". Confirm.
- [ ] RQ Job list, queue `passport_extraction`: the jobs appear and finish;
      `long` gets no new OCR jobs.

## 6. Smoke test on live

Extraction and queue
- [ ] Upload one passport through a test file collection → Passport
      Extraction leaves `Queued` within a minute and finishes in about 1–2
      minutes; its RQ job ran on `passport_extraction`.
- [ ] Retry one of the failed "No machine-readable zone" records whose
      upload is a valid passport (Retry button) → expect **Needs Review**,
      error "Part of the machine-readable zone could not be read…", with the
      number, birth date and expiry filled in. Check them against the
      passport and **Verify**. The tracking application links as usual.
- [ ] A wrong upload (not a passport) still fails with "No machine-readable
      zone was detected".

Tracking and WhatsApp
- [ ] A status change on a pilot Process File updates the tracker and, for a
      zone with `notify_visa_tracking_updates` on, sends the "Visa Tracking
      Update" template with the static button (no Meta 400 in Error Log).
- [ ] WF Settings: `retry_error_codes`, retry interval (25 h), max attempts
      (3) and max age (72 h) are set; scheduler is on. A send that Meta rejects
      at once is logged in Error Log and is not retried; delivery failures
      with a listed code are retried by the hourly sweep.
- [ ] Public tracker: correct passport + DOB opens the case; a client with two
      cases sees the list.

Health
- [ ] Error Log: no new passport_extractor or visa tracking errors.
- [ ] Worker memory under load with two OCR jobs.

## 7. After go-live

- [ ] The ~80 failed "No machine-readable zone" extractions do not re-run by
      themselves. Retry the valid passports (Retry button, one by one) to get
      them into Needs Review with fields filled in.
- [ ] Daily: Needs Review (verify within a working day), Failed, Error Log,
      `passport_extraction` backlog.
