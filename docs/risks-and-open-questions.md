| 18 | **STILL LIVE as deployed: FEAT-001 rate limiting on site `visaguy` does not constrain credential enumeration.** `verification.py:102` sets `target_bucket = candidates[0][0]`, scoping the failure counter per exact passport+DOB pair. An attacker knowing a passport number can enumerate DOBs (~36,500 for an adult) from one IP. Close this risk only after TASK-012 is committed and deployed to `visaguy`, per its own "Completion evidence" section. | Security | runtime-verified |

| 24 | **A genuinely non-JSON request body to the public `verify_identity` endpoint returns a raw traceback page on an unauthenticated endpoint.** Frappe's own `make_form_dict` parses the request body **before** the app's handler runs, and raises there for malformed (non-JSON) input — outside the app's `UnsafeRequestError` path entirely, so the app's own generic-failure/constant-response handling never gets a chance to apply. This is a pre-existing Frappe-core behaviour, not a defect introduced by `verification.py`. By contrast a valid-JSON-but-wrong-shape body (e.g. `[]`) is caught correctly by the app's `UnsafeRequestError` path and returns the byte-identical generic body. Consequence: information disclosure (a stack trace on a public endpoint) and it defeats the constant-response property this feature otherwise maintains, in this one reachable case. Found 2026-09-01 during TASK-012 live-HTTP testing; not caused by that task's changes. See TASK-014. | Security | runtime-verified |
| 25 | **An untracked administrative action deleted hundreds of Custom Fields and Property Setters across many doctypes on `visaguy`, including three this feature depends on, and nothing in committed code explains it.** `tabDeleted Document` records three FEAT-001 Custom Fields — `Lead-custom_visa_tracking_application`, `PF Process File-custom_visa_tracking_application`, `PF Process File-custom_client_status` — explicitly deleted 2026-08-07 (owner `Administrator`), with DB columns surviving but the fields not rendering. The same `tabDeleted Document` window (14:00-19:00 UTC that day) also contains many hundreds of `Property Setter`/`Custom Field` deletions across unrelated doctypes (`Sales Order Item`, `Item Barcode`, `FF Document`, and others) — ruling out a hand-picked, visa-tracking-only deletion. The blast radius and timing best fit an unfiltered fixture-reconciliation sweep (`bench migrate` against a bare-string `"Custom Field"`/`"Property Setter"` fixture entry, which prunes anything not present in the export), and the exact mechanism that would produce this pattern exists in `visaguy_crm/visaguy_crm/hooks.py` and `visaguy_hrms/visaguy_hrms/hooks.py` — but both are commented out and have been since their earliest committed history, so no currently-live code path explains the incident. The likely cause is a local, uncommitted hooks.py edit or a manual Desk/console action that left no repository trace. **Features beyond visa tracking may be silently affected** by the wider deletion set, and because nothing in committed code explains the trigger, it could recur without warning. See `ongoing/visa-tracking-client-status/01-recon.md` ("Secondary question — the three missing Custom Fields") for the full evidence, and TASK-016/ADR-010 for the feature-specific consequence (the derived client-status write target does not currently exist). | Architecture | runtime-verified |

| 26 | **No longer theoretical: confirmed root cause of real test-isolation damage, severity raised.** `visaguy_crm`'s Lead hooks call `frappe.db.commit()` mid-transaction on every Lead save. This is a production atomicity concern, not merely a test nuisance: an unconditional commit partway through a Lead save means a later failure in the same request can no longer be rolled back, leaving a partially-applied change permanently on the record. It also interacts badly with `FrappeTestCase`'s class-level-only rollback — a row a test creates and deletes mid-test can be permanently committed and leak into the next run instead of being rolled back with the rest of the transaction. This is the same leaked-state failure mode that caused three test-isolation failures on 2026-09-01 (see `ongoing/visa-tracking-implementation/12-session-2026-09-01-task-011-012.md` §2b), and was confirmed as a contributing mechanism during TASK-016's test-environment correction on 2026-09-02 (see the session report `ongoing/visa-tracking-implementation/13-session-2026-09-02-task-016.md`). **Confirmed 2026-09-03: 811 synthetic `Contact`, 509 `Lead`, and 1 `Customer` rows survived test rollback and accumulated on the test site until naming collisions broke the suite** — this is not a hypothetical leak, it is the actual damage this mechanism does at real accumulation. Three still-unfixed sites are the confirmed cause, all outside the two Lead customer-sync hooks already fixed in `visaguy_crm 51f608e`: `form_disable_via_pf_action.py` (PF Process File `validate`), `allocated_to_process_file.py` (ToDo `after_insert`), and `file_collection_from_lead.py` (FF File Collection `before_save`). See TASK-018 for the investigation and fix. | Data integrity | runtime-verified |
| 27 | **A rebuilt test site that omits `visaguy_crm`/`hrms` produces a green suite that does not reflect production**, because the constraints those apps enforce simply are not present to fail against. | 28 | **A primary's `custom_dependent_details` child table lists Process Files belonging to unrelated primaries, causing the public tracker to show unrelated people as dependants.** Found 2026-09-02/03 while implementing the dependant status-display feature (ADR-010 "Amendment (2026-09-03)", TASK-016). Primary `Schengen-Primary-00127-ANNETTE ENGELBRECHT-6863`'s `custom_dependent_details` table lists two Process Files that belong to two other, unrelated primaries — one a different Schengen case, one a China case. Client-visible consequence: that primary's tracker lookup would show two unrelated people (masked names only, via the existing masking helper — no Process File or application identifiers are exposed) as their dependants, one primary out of 701 checked. **Not fixed, by explicit owner decision:** the owner rejected a proposed defensive fix (cross-checking each `custom_dependent_details` entry against the dependant's own `custom_primary_process_file` back-link before displaying it) on the grounds that cross-checking two sources that are supposed to agree hides the disagreement rather than fixing it — a wrong entry is a bug to fix at its origin, in the data. | 29 | **`the_visaguy` ships both `custom_field.json` and `custom_fields.json` as fixtures.** Frappe's fixture sync imports every `.json` file present in an app's `fixtures/` directory — it does not require or expect a single canonically-named file per fixture type. With both `custom_field.json` and `custom_fields.json` present, two files claim authority over the same underlying `Custom Field` records, which is fragile: divergent entries for the same field name between the two files, or one file omitting a field the other adds, would produce an outcome that depends on load order/last-write-wins rather than a single readable source of truth. Not yet observed to have caused an incorrect field on `visaguy`, but the ambiguity itself is the risk. Recommendation: consolidate into a single `custom_fields.json` (the plural form is Frappe's conventional name for this fixture type) before this reaches a live site, and delete the other. | Configuration | source-wired |
| 30 | **Valid passports are rejected into `Needs Review` because the MRZ validator mishandles an unused optional-data field.** Confirmed 2026-09-03 on a real production extraction: a Ghanaian passport at roughly 95% OCR confidence, with the passport-number, date-of-birth, expiry-date and composite check digits all valid, was classified `Needs Review` solely because `personal_number_check_valid` was false. Ghana leaves MRZ line 2 positions 29–42 unused, so the check digit at position 43 is the ICAO filler `<`; ICAO 9303 Part 4 permits this (some issuers write `0`), but the validator compares its computed `0` against the `<` it read and fails. TASK-003 §4.4 then dropped `mrz_valid` on that one flag, and §5.3 independently routed the record to review for it. Client-visible consequence: passports that need no human review are queued for it, so tracking is delayed by operator throughput rather than by anything wrong with the document — and the rejection rate is issuer-dependent, concentrated on nationalities that leave optional data blank. Fix specified in TASK-019 and in TASK-003 "Amendment (2026-09-03)"; **not yet implemented or deployed**, and the backfill of already-affected records is assessed but deliberately not executed pending a client-visible cascade check. | Functionality | runtime-verified |
| 31 | **Passport extraction now depends on a manual staff action, and its absence fails silently.** Since ADR-012 (2026-09-03) a configured passport row enters extraction only when `FF File Collection File.status` becomes `Completed`. If staff never mark the row Completed — or mark a different row, or the case is handled entirely outside FileFlo — there is no `Passport Extraction`, therefore no `Visa Tracking Application`, therefore no public tracking, and nothing anywhere reports this: no error, no log line, no queued job. From the client's side the tracker simply says the same generic failure it says for a wrong passport number. The compensating control is the backfill job (`enqueue_missing_fileflo_extractions`) and the read-only missing-extraction report, but both were narrowed to `Completed` rows in the same change, so neither can catch this particular case by design. Mitigation is operational, not technical: the runbook's diagnostic order now starts with "is the passport row Completed?". | Operations | source-wired |
| 32 | **The applicant name lost its constant-shape guarantee; a nameless application now sends an empty string.** Before the ADR-005 2026-09-03 amendment, `mask_applicant_name` returned the fixed placeholder `*****` for a blank, whitespace-only, or `None` name. The replacement returns `(value or "").strip()`, so an application whose verified extraction carried neither `given_names` nor `surname` puts `""` on the wire under `applicant_name`. The response shape is still constant (the key is always present, never null) but the *rendered* result is not: the SPA shows an empty name where it previously showed a placeholder, and no test asserts what that looks like on screen. Not yet observed on real data — every extraction reaching `Verified` has passed MRZ parsing, which yields a surname — but it is reachable and unhandled at the UI level. | Functionality | source-wired |
| 33 | **The Completed-row trigger and the applicant-name rename have suite evidence but no live-traffic evidence.** As of 2026-09-03 the on-site suite is green — `bench --site visa-tracker-test.localhost run-tests --app the_visaguy --skip-test-records` → **366 tests, OK** — and the frontend is 64/64, so both changes are exercised in-process on a real site.
