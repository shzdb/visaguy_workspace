## Design notes and deviations

### How the fixture gets to a site

- Frappe v15 `frappe.utils.fixtures.import_fixtures` imports **every** `*.json` file
  in `<app>/fixtures/` during migrate. It does not use the `fixtures` list in `hooks.py`
  (verified read-only in `/home/shahzad/bench/apps/frappe/frappe/utils/fixtures.py`).
  The existing `custom_docperm.json` already depends on this: `Custom DocPerm`
  is not in the `hooks.py` `fixtures` list. So this task needs no `hooks.py` change.
  **Deviation from task §4 ("filtered by name")**: there is no `hooks.py` entry,
  filtered or bare. The file is imported as it is, so only these 64 named rows are
  imported, and the effect is the same as a filter by name. A hooks entry would only matter for
  `bench export-fixtures`, and `hooks.py` `fixtures` belongs to TASK-032 (see "Needs from another task").
- The import path is `import_file_by_path(..., data_import=True, force=True)` →
  `import_doc`. If a document with the same name exists, the importer deletes it
  and inserts the fixture copy again. It sets `doc.flags.ignore_links = True`, so a role
  that does not exist on a site does **not** break migrate. The row stays inert
  until the role exists. The `CustomDocPerm` controller only clears the DocType cache
  in `on_update`.
- `frappe.model.meta.Meta.set_custom_permissions` replaces `meta.permissions`
  with the Custom DocPerm rows when at least one row exists for the parent (verified
  read-only). This is why the fixture must contain the full union.

### Record format (D1)

- The fields and key order are the same as in the existing rows: all 15 flags written out,
  `docstatus 0`, `parentfield "permissions"`, `parenttype "DocType"`,
  1-space JSON indent, and no trailing newline (as in the original file).
- Name scheme: `<Role>-<Parent>`, as in the existing rows. For the one permlevel 1
  row, the name has the suffix `-<permlevel>`: `Passport Extractor User-Passport Extraction-1`.
- New rows have `modified` = `2026-09-28 12:00:00.000000`. The import uses
  `force=True`, so it does not compare timestamps.

### Flags chosen

- Read roles get `read: 1` only. `select` is 0 because the existing rows use 0.
  `print`, `email`, `export`, `report` and `share` are 0 (least privilege). `read` is
  enough for the form view, the list view and the Link search that the
  `custom_client_status` picker uses (TASK-027). The Report view needs `report`, which is not granted.
- Operations roles on the Application get `read: 1, create: 1, write: 0`. A user with
  `create` and no `write` can save a new Application from the desk. After the save,
  the form is read-only. The main path is the TASK-031 server action.
- Operations roles on Passport Extraction get `read: 1, write: 1` at permlevel 0. All other
  flags are 0.

### Deviations and interpretations

1. **`Visa Tracker Operator` keeps `write` on `Visa Tracking Application`.** Task §3
   names only `Visa Tracker Manager` and `System Manager` as writers. The Operator
   write is in the existing fixture row and in the standard DocType JSON, and the orchestrator
   said to keep the existing Manager/Operator rows. So the D7 test
   allows writers ⊆ {System Manager, Visa Tracker Manager, Visa Tracker Operator}
   and checks that none of the 16 listed roles has write. No user holds
   `Visa Tracker Operator` on `visaguy` (task context). See Open questions.
2. **`Visa Tracker Settings` has no `System Manager` row in the fixture**, but the
   standard JSON has one. This gap existed before this task. On any site where the fixture's
   Settings rows are the only Custom DocPerm rows, a non-Administrator `System Manager`
   cannot open Settings. D5 says to add no new rows, so it is not fixed here. The test for this
   area only checks that none of the 16 read roles can open Settings. See Open questions.
3. `System Manager` on Passport Extraction has no permlevel 1 row in the standard JSON.
   It is copied as it is, so this behaviour does not change.
4. Passport Extraction rows on a site where `passport_extractor` is not installed
   (for example `visaguy` today): the rows are imported but stay inert. When the app is installed later, they
   take effect at once, and because of the union, `System Manager` and `Passport Extractor User`
   keep their access.

## Needs from another task

- **TASK-032 (`hooks.py` `fixtures`)**: no change is needed for this task, because migrate imports every fixture JSON.
  Do **not** add a bare `"Custom DocPerm"` entry. With one, `bench export-fixtures` would dump
  all Custom DocPerm rows of the site over this file. If a hooks entry is wanted for export,
  it must filter by the 64 names in this file.
- **TASK-033 (Passport Extraction review)**: operations users have write at permlevel 0 only.
  Frappe resets any permlevel 1 field that the user cannot write to its stored value on save.
  So if the correct/verify action changes `error_message` (permlevel 1) or other
  permlevel 1 fields under the user's permissions, the change is silently dropped.
  Either set those fields in a server-side step with `ignore_permissions`, or leave them unchanged.
- **TASK-031 (manual actions)**: as the task says, check the two operations roles on the server and
  create the Passport Extraction with `ignore_permissions` (operations users have no
  `create` on Passport Extraction). They do have `create` on `Visa Tracking Application`,
  so the Application insert can use normal permission checks.
