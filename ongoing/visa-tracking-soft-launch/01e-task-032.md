## Design notes and deviations

### PF Process File field order (verified against Frappe v15.113 source)

- `frappe.model.meta.Meta.sort_fields` gives priority to a `field_order`
  Property Setter over `insert_after`. visaguy_crm ships
  `PF Process File-main-field_order` in
  `visaguy_crm/visaguy_crm/custom/pf_process_file.json` (modified
  2026-08-14). Its list does **not** contain
  `custom_visa_tracking_application`, `custom_client_status` or any of the
  new fields. So `insert_after` still places them, and this matches the
  FACTS order. `custom_section_break_mw0ux` is in that `field_order` directly
  after `custom_form_submitted`. So the new section (the only
  `insert_after` = `custom_form_submitted` that is not in `field_order`) goes
  between the two, and the chain resolves through
  `_update_field_order_based_on_insert_after`.
- Result: `custom_form_submitted`, **`custom_visa_tracking_section`,
  `custom_visa_tracking_application`, `custom_client_status`,
  `custom_tracking_empty_note`, `custom_tracking_column_break`,
  `custom_tracking_updated_on`, `custom_tracking_enabled`**,
  `custom_section_break_mw0ux`.
- `custom_lead_file_collection` has `insert_after` = `file_collection` and is
  listed in `field_order`. It now comes directly after `file_collection`, so
  the old section loses nothing else.
- Risk 1: if the site's `field_order` Property Setter ever lists the two
  moved fields (for example, after someone saves Customize Form for PF
  Process File), `field_order` wins and they stay in the old section. This
  is an on-site check.
- Risk 2: without any `field_order` Property Setter, both
  `custom_section_break_mw0ux` (visaguy_crm) and the new section have
  `insert_after` = `custom_form_submitted`. Their order then depends on
  Custom Field `idx`, and the new section could come after the Application
  Form section break. There is no way to avoid this without changing
  visaguy_crm. It does not apply while the visaguy_crm `field_order` is
  present.

### PF field details

- The section is `collapsible = 1` without `collapsible_depends_on`, so
  Frappe shows it collapsed by default. This follows the contract.
- The note is an HTML field with
  `depends_on = eval:!doc.custom_visa_tracking_application`. Its content is
  `<p class="text-muted small">No tracking yet. It is created after the
  passport is marked Completed and verified.</p>`.
- **Addition:** `custom_tracking_updated_on` and `custom_tracking_enabled`
  have `depends_on = eval:doc.custom_visa_tracking_application`, the same as
  `custom_client_status`. Without it, a read-only unchecked Check would show
  on unlinked files.
- The fetched fields have `fetch_if_empty = 0` and `no_copy = 1`. Frappe
  refreshes them when the PF Process File is saved, or when the link is set
  in the form. Between saves they can be stale. See "Needs from another
  task" and "Open questions".
- `custom_client_status` is unchanged. Its `fetch_from`, `fetch_if_empty`,
  `depends_on`, `link_filters`, `read_only` and `description` from TASK-027
  are the same. `custom_visa_tracking_application` changed only in
  `insert_after` and `modified`.
- `modified` was set to `2026-09-28 12:00:00` on every changed or new
  record. Fixture import replaces the record anyway. The value only helps
  to trace the change.

### Hooks and fixture registration (risk 25)

- `custom_fields.json` and `property_setters.json` are hand-maintained
  files. `frappe.utils.fixtures.import_fixtures` imports every `*.json` in
  `fixtures/`, whatever is in the hooks list. The existing records there
  (for example `PF Process File-custom_visa_tracking_application`) are not
  in the hooks `Custom Field` filter either. The hooks list only drives
  `export-fixtures`, which writes `custom_field.json` and
  `property_setter.json` (different file names). Adding the new names to
  the hooks lists would create duplicate records on the next export. So I
  followed the existing convention: no hooks change for Custom Field or
  Property Setter. No bare-string entry exists, and a test enforces this.
- `workspace.json` *is* the hooks-exported file for Workspace, so
  "Visa Tracking" was added to that name filter.

### Property Setters

- `property_setters.json` had no records to copy. I used the standard
  Frappe export shape (checked against
  `visaguy_crm/fixtures/property_setter.json`):
  `doctype_or_field = DocField`, `property = hidden`,
  `property_type = Check`, `value = "1"`, `module = The Visa Guy`, names
  `<DocType>-custom_visa_tracking_application-hidden`.
- The Lead, CRM Lead and Customer Custom Field records were not changed and
  not deleted (risk 39).

### Visa Tracking Application DocType

- Layout fields added: `applicant_section`, `applicant_column_break`,
  `status_column_break`, `timeline_section`, `timeline_html`. No existing
  field was renamed, removed or retyped, and a test enforces this.
  Permissions were not changed.
- **Label change only:** the `public_state_section` label changed from
  "Public State" to "Current Status", as the contract requires. The
  fieldname is unchanged.
- `references_section` and `secure_lookup_section` now have
  `collapsible = 1`. The Secure Lookup label is unchanged.
- The list view columns are `applicant_display_name`, `destination`,
  `current_status`, `tracking_enabled` and `status_updated_on`. Frappe shows
  the title field as the subject column, and it does not repeat it. The
  standard filters are `current_status`, `destination`, `tracking_enabled`
  and `application_closed`. `search_fields` is
  `applicant_display_name,process_file,lead`.
- `links`: `{link_doctype: Visa Tracking Status Log, link_fieldname:
  tracking_application}`.
- DocType `modified` was bumped to `2026-09-28 12:00:00`, so `bench migrate`
  syncs the DocType again.
- Form script:
  - On refresh, it adds "Open Process File" (only when `process_file` is
    set) and fills `timeline_html`.
  - It uses `frappe.db.get_list("Visa Tracking Status Log")` with the
    filter `tracking_application`, the fields `effective_on`, `new_status`,
    `visible_to_client` and `changed_by`, ordered by `effective_on desc`,
    with a limit of 50. **Note:** the status field on the log is
    `new_status`, not `status`.
  - All values are HTML-escaped. `changed_by` is shown through
    `frappe.user.full_name`.
  - The helpers are form events (`frm.trigger`), plus one uniquely named
    global function, so that a repeated evaluation of the doctype JS does
    not fail.
- List script (the contract lists the file but does not say what it
  does): an Open (blue) or Closed (gray) indicator from
  `application_closed`. It does not repeat the tracking-enabled column.

## Needs from another task

- **TASK-031 (lifecycle and ensure service), recommendation only.** If the
  ensure or lifecycle path sets `PF Process File.custom_visa_tracking_application`
  with `frappe.db.set_value` (no document save), `fetch_from` does not run.
  `custom_tracking_updated_on` and `custom_tracking_enabled` then stay empty
  until the next PF save. The fix is to set them in the same `set_value`
  call: `status_updated_on` goes to `custom_tracking_updated_on` and
  `tracking_enabled` goes to `custom_tracking_enabled`. The owner of the
  status service can do the same when the status changes.
- **TASK-034:** the timeline needs read on `Visa Tracking Status Log`, and
  the workspace shortcuts need read on `Passport Extraction` and
  `Visa Tracking Application` for the operations roles. TASK-034 already
  plans all of these.
