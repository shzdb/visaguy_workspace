## Summary

TASK-033 is implemented in the `passport_extractor` repository on branch
`sl/task-033`. The branch has one commit on top of `0febf6c`.

- Contract C1 is implemented. `create_retry_extraction` (server-side helper,
  no permission check) and the whitelisted `retry_extraction` (checks create

  values), the Retry extraction button, a file preview at the top of the form,
  and a red expiry note.
- The list script adds status indicators. The DocType JSON adds list columns,
  standard filters and search fields.
- 25 new pure tests pass on the bench. The existing pure tier is unchanged
  from the baseline.
- No import of `the_visaguy`, FileFlo, ProcessFlo or Lead was added (ADR-003).

## Design notes and deviations from the task contract

1. **Module location.** The task front matter lists
   `passport_extraction.py` as an expected file. Contract C1 puts the retry
   functions in `passport_extractor.passport_extractor.api`. I put
   `verify_extraction` in the same module so that all desk actions are in one
   place. `passport_extraction.py` is unchanged. The controller already
   allows `Needs Review -> Verified`, and `_validate_verified_state` and
   `_preserve_verification_audit` work with the explicitly set audit fields.
2. **`status` is not `read_only`.** The task Context says the field is
   `read_only`. In the DocType JSON it is not. I did not change it, because
   the contract says "do not change field permissions".
3. **Order of verify checks.** The order is permission, then status, then
   values. A user without write permission cannot find out the record status
   from the error.
4. **Only review fields are accepted.** `values` can be a dict or a JSON
   string. Only the six review fields are read. Other keys (for example
   `verified_by` or `mrz_valid`) are ignored. Strings are stripped. Dates must
   be ISO `YYYY-MM-DD`, which is what the desk Date control sends. An invalid
   date or a non-object value raises `ValidationError`. The error messages
   contain field labels only, never values.
5. **Verification note.** Format:
   `Values checked by hand against the passport file. Changed fields: Passport Number, Surname.`
   If nothing changed, the note says `No values were changed.` If the user
   added notes, the text `\nReviewer notes: <user notes>` is appended. The
   note uses field labels, not raw fieldnames. It never contains an old or new
   value. The note replaces any earlier `verification_notes`.
6. **Values are not upper-cased.** Values are stripped only.
   `passport_number_normalized` is still derived by the controller
   (`_normalize_values`) on save, and the lookup hash uses that value.
7. **`requires_review` and `error_code` are not changed on verify.** They
   show why the record needed review. The contract did not ask to clear them.
8. **Retry job id (addition to C1).** `create_retry_extraction` makes a
   `uuid4` job id, stores it in `last_job_id` on the new record (in the insert
   dict, so there is no second write), and passes `job_id=` to
   `frappe.enqueue`. This matches `the_visaguy` `extraction_orchestrator`.
   Every C1 argument is present as specified: job path, `queue="long"`,
   `passport_extraction_name=<new>`, `enqueue_after_commit=True`.
9. **Missing record on retry.** A missing record raises
   `frappe.DoesNotExistError`. This is a subclass of `frappe.ValidationError`,
   so C1 ("raises ValidationError") still holds.
10. **Retry bounds.** `_enforce_retry_bounds` and `MAX_RETRY_COUNT` control
    the in-place `Failed -> Queued` transition on the same record. The C1
    retry creates a new record, and `before_insert` always resets its
    `retry_count` to 0. So those bounds do not apply, and C1 does not ask for
    a limit. The failed record is not written: it is read with
    `frappe.db.get_value` using explicit fields. The old in-place
    `services/extraction_service.retry_extraction` is unchanged and not used
    by the new UI.
11. **File preview placement.** The form preview is a dashboard section
    (`frm.dashboard.add_section`) at the top of the form. I did not add an HTML
    field, because the contract forbids field-order changes. Frappe removes
    custom dashboard sections on every refresh, so the preview is not
    duplicated. Images (`jpg`, `jpeg`, `png`) use an `<img>` tag and PDFs use
    an `<iframe>`. Other types show no preview on the form, and the dialog
    shows "No preview available". The URL is HTML-escaped.
12. **Expiry note.** `frm.set_intro(..., "red")` shows "This passport has
    expired." when `expiry_date` is before `frappe.datetime.get_today()`.
    Otherwise it clears the note. It does not block anything.
13. **Button visibility.** Verify shows only when `status == "Needs Review"`
    and `frm.has_perm("write")`. Retry extraction shows only when
    `status == "Failed"` and `frappe.model.can_create("Passport Extraction")`.
    Retry asks for confirmation, uses `freeze`, and then routes to the new
    record. There is no Reject button, and `Extracted` records get no Verify
    button.
14. **Permlevel-1 fields.** The dialog, list and search fields use only
    permlevel-0 fields. `mrz_line_*`, `raw_ocr_text`, `raw_extraction_result`
    and `error_message` do not appear.
15. **Test location.** The existing pure tests are in
    `doctype/passport_extraction/test_passport_extraction.py`. They are mixed
    with site-bound classes, and
    `unittest discover -s passport_extractor [-t .]` cannot find them because
    `passport_extractor/passport_extractor/doctype/` has no `__init__.py`
    (that command runs 0 tests). So I added a new package
    `passport_extractor/passport_extractor/tests/`. The package runs under
    `unittest discover -s passport_extractor -t .` without a site.
    `bench run-tests --app passport_extractor` will also collect it. I did not
    add `doctype/__init__.py`, so that the discovery of the existing tests
    stays the same.
16. **How the tests mock frappe.** The tests use the same pattern as
    `the_visaguy` pure tests: `frappe` is patched as a module inside `api`,
    and the real exception classes and `parse_json` are restored on the mock.
    Frappe's whitelist wrapper reads `frappe.local.flags.in_test` on each
    call, so the tests bind `frappe.local.flags` with
    `patch.object(..., create=True)`.

## Needs from another task

- **TASK-034 (`custom_docperm.json`).** `Operations Associate` and
  `Operations Team Lead` need permlevel-0 `read` and `write` on Passport
  Extraction, so that the Verify button shows and `verify_extraction` passes.
  They also need `create` if they are expected to use the form's Retry
  extraction button. TASK-031's Process File action calls
  `create_retry_extraction` directly and does not need this.
- **TASK-034 or the owner (private file access).** The preview loads the
  private `/private/files/...` URL. Frappe serves it only if the user can read
  the `File` record, which usually means read access on the document the file
  is attached to (probably `FF File Collection`). If the Operations roles do
  not have that access, the preview shows a broken image or a 403 error, but
  Verify still works. This needs an on-site check and maybe a read DocPerm.
- **TASK-031.** Consume C1 lazily:
  `frappe.get_attr("passport_extractor.passport_extractor.api.create_retry_extraction")(name)`.
  The helper raises `frappe.ValidationError` for a non-`Failed` status and
  `frappe.DoesNotExistError` (a subclass of ValidationError) for a missing
  record. It returns the new record name. The new record's `last_job_id`
  holds the enqueued job id.

## Open questions

1. **Retry has no de-duplication.** Each Retry click on the same `Failed`
   record creates another new record. The button asks for confirmation and
   routes to the new record, which reduces double clicks, but the server
   does not stop them. Should `create_retry_extraction` refuse when a
   `Queued`/`Processing` retry already exists for the same file and source?
   This would change C1 ("raises unless Failed"), so it was not done.
2. **Retry has no limit.** A new-record retry resets `retry_count`, so
   `MAX_RETRY_COUNT` does not limit repeated manual retries. Is a limit per
   source or per file wanted?
3. **Verified records keep their review markers.** Should verification clear
   `requires_review` or `error_code`, or keep them as history (current
   behaviour)?
4. **Should values be upper-cased?** Should the verify step upper-case
   `passport_number`, `nationality` and the names to match the MRZ style?
   Currently values are only stripped. Matching and lookup use the normalized
   number, so this is cosmetic.
