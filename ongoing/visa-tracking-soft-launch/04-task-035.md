## Design notes and deviations

### Row set and filters

- By default the report shows the open states of ADR-016: `Unassigned`,
  `Assigned`, `Inprogress` and `Hold`. The workflow state filter is a Select
  with every state. When it has a value, the report shows only that state, and
  this can be a closed state.
- The department filter uses `custom_department` (Link Department, from
  visaguy_crm).
- "Modified from" uses `modified >= date`. "Modified to" uses
  `modified < date + 1 day`, so the whole end day is included.
- The Process Files come from `frappe.get_list`, so user permissions and
  permission query conditions on PF Process File apply. The other tables are
  read with `frappe.get_all` (no permission check), because no value from
  them is shown except the reason code.
- `only_without_tracking` removes linked rows from the table after the summary
  is computed. So the summary always shows the totals for the filters, and
  the check box does not reset "Tracked" to 0.

### Columns

The columns are Process File (link), applicant name (`applicant_name`),
workflow state, destination (`PF.custom_destination`), primary or dependant
(dependant when `custom_primary_process_file` is set), modified, tracking
application (link), tracking status, reason (code), and next step.

- **Tracking status** is `PF.custom_client_status`. This field is fetched from
  `Visa Tracking Application.current_status` (TASK-027), so no extra query is
  needed.
- **Addition:** a "Next Step" column. It shows the text from TASK-031's
  `api/desk.OUTCOME_MESSAGES`. Three messages are replaced for report
  context: `extraction_queued` and `linked_existing` (the report queues and
  links nothing), and the new `not_saved_since_launch`.

### Reason order (K2)

The report checks the reasons in this order. It is the order of
`TrackingEnsurer.run`, with the launch date added after step 2.

1. `already_linked`: `custom_visa_tracking_application` is set.
2. `excluded_state`: the workflow state is `Rejected`. This can happen only
   when the Rejected state is selected in the filter.
3. `not_saved_since_launch`: the launch date filter is set, and
   `date(modified) < launch date`. When the filter is empty, this check is not
   used. It comes before the inspection steps, because a file that nobody
   saved never reached the save hook. That is the cause, whatever the
   passport rows show.
4. `linked_existing`: exactly one active application (`application_closed = 0`)
   exists on the lead-stage or process-stage collection. If there are two or
   more, the report continues to the next steps, as `ensure_tracking` does.
5. `not_configured`: `passport_field_ids` is empty.
6. Passport rows: rows of `FF File Collection File` whose `field_id` is in
   `passport_field_ids`, in the collections of the file. File names are never
   matched. For each row:
   - not `Completed` → `ROW_NOT_COMPLETED`;
   - `document` → `FF Document.attach` → a private `File` (found by URL or by
     name, as `resolve_fileflo_file` does). If there is no such file, the
     report uses a skip reason that maps to `passport_no_file`;
   - the newest `Passport Extraction` with the same key as
     `find_existing_extraction` (source collection, field_id, row, file URL).
     No extraction → `created`. `Failed` → `FAILED_RECORD_EXISTS`. Any other
     status → `reused`.

   Then `ensure_service.outcome_for_rows` gives the outcome, with the TASK-031
   priority. If the file has no rows and one of its collections does not
   exist → `inspection_error`.
7. Verified extraction and no link: for each collection with a Verified
   extraction, the report checks, in order:
   - the collection has no Lead reference → `no_source_lead`;
   - `auto_create_tracking_application` is off → `not_configured`;
   - no applicant row matches (`_match_applicant_row`) →
     `applicant_row_unresolved`;
   - the matched row already links an application → no blocker;
   - a `duplicate_identity_in_lead` review flag exists for the Lead →
     `duplicate_identity_in_lead`;
   - the Lead has no `custom_destination` → `no_destination`.

   If nothing blocks → `verified_not_linked`.

### Deviations and interpretations

1. **The `enabled` and `enable_passport_extraction` switches do not decide the
   row reason.** `ensure_tracking` returns `disabled` or `not_configured` for
   every file when these switches are off. The report must explain coverage on
   `visaguy` before tracking exists (Validation 2), so it ignores the switches
   and shows "Visa tracking: Off" in the summary. `disabled` is therefore never
   a row reason. An empty `passport_field_ids` still gives `not_configured`,
   because without it the report cannot find passport rows.
2. **Reasons not in the TASK-035 list.** The report can also show
   `linked_existing`, `extraction_queued`, `not_configured`,
   `inspection_error`, `no_source_lead`, `verified_not_linked` and
   `excluded_state`, because `ensure_tracking` returns them for the same cases
   (see 01b, deviation 1). The most common legacy case is a Completed passport
   row with a private file and no extraction. For this case the reason is
   `extraction_queued`, and the Next Step column says that nothing is queued
   yet.
3. **`applicant_row_unresolved` and `no_destination` are computed, not read
   from Error Log.** The brief lists Error Log flags as the source for three
   reasons. For two of them the report computes the result from current data:
   one bulk query on applicant rows, and one on the Lead destination, for the
   Leads of Verified-but-unlinked files only. A review flag stays for 7 days or
   more after staff fix the Lead, so a flag can be stale. The computed value is
   the same check that `diagnose_tracking_creation` makes.
   `duplicate_identity_in_lead` still comes from the flag
   (`Error Log.method` = the flag title, with the Lead as reference), because
   the identity comparison needs the lookup hash, and the hash is made from
   the passport number and DOB. A test checks that the flag title is still
   present in `lifecycle_service.py`, so a rename there breaks a test.
4. **"Latest Passport Extraction per collection"** is done per row key
   (collection, field_id, row, file URL), newest first. `find_existing_extraction`
   works this way. There is still one query per batch of collections.
5. **A linked applicant row is not a blocker.** `diagnose_tracking_creation`
   returns "no blocker" only if the linked application has the same identity.
   The report cannot compare identities without passport values, so for a
   linked row it always returns `verified_not_linked`.
6. **TASK-032's workspace test changed.** `test_shortcuts` asserted exactly
   four DocType shortcuts. After the new Report shortcut, the test would fail.
   The change adds one expected tuple, and allows type `Report` for
   `Visa Tracking Coverage` only. This phase gave me `workspace.json`, and the
   test must match that file.
7. **Report roles include `Desk User`**, because K4 says to reuse TASK-034's
   list. Frappe v15 also requires `report` permission on `ref_doctype`
   (`query_report.get_report_doc` and `run`). In the bench fixtures
   (visaguy_crm and visaguy_hrms `custom_docperm.json`), only
   `Operations Associate`, `Operations Team Lead` and `System Manager` have
   `report` on PF Process File. So in practice only these roles can run the
   report. Other roles can see it, and Frappe answers "You don't have
   permission to get a report on: PF Process File". See Open questions.
8. **Summary instead of a first data row.** K3 allows either one. I used a
   summary, because a data row would break sorting, export and the column
   types.

### Timing note (K6)

The number of queries depends only on the number of batches (`CHUNK_SIZE` =
5000 names), not on the number of rows. There are no per-row queries. Estimate
for 15,000 open files (at most 30,000 collection names):

| Query | Count |
|---|---|
| `PF Process File` (`get_list`) | 1 |
| `FF File Collection` (existence and Lead reference) | ⌈C/5000⌉ ≤ 6 |
| `Visa Tracking Application` (active, by `file_collection`) | ≤ 6 |
| `FF File Collection File` (by `parent`, with the field_id filter) | ≤ 6 |
| `FF Document` (only for Completed rows) | ⌈D/5000⌉ ≈ 2 |
| `File` by URL (indexed `file_url(100)`), and `File` by name | ≈ 2 + ≤ 1 |
| `table_exists("Passport Extraction")` + `Passport Extraction` by `source_document` | 1 + ≤ 6 |
| Verified path: Applicant Information, Lead / CRM Lead, Error Log | ≈ 3–4 |
| Visa Tracker Settings | 0–1 (cached) |

The total is about 35 queries at most. The Python work is linear, with
dictionary lookups for each file and each row. `test_query_count_does_not_grow_with_files`
checks that 3 files and 40 files give the same number of queries, and
`test_queries_are_batched_by_chunk_size` checks the batching.

Risk: `Passport Extraction.source_document` has no index (passport_extractor
indexes only `file_hash`), so that query scans the table. The table is small
during the soft launch. See "Needs from another task".

## Open questions

1. Should the report roles be narrowed to the roles that can run it
   (`Operations Associate`, `Operations Team Lead`, `System Manager`)? With
   `Desk User` in the list, every desk user sees the report, and most of them
   get a permission error when they run it.
2. Should `not_saved_since_launch` come before `linked_existing`, as it does
   now? A file with an existing application that nobody saved is shown as
   "not saved". The next save links it in both cases.
3. Should the report also show `disabled` for every row when tracking is
   off, as `ensure_tracking` does? It does not now (deviation 1), so that the
   counts on `visaguy` are useful before the launch.
4. Should the summary label change from "Open files" to "Files" when the
   workflow state filter selects a closed state?
