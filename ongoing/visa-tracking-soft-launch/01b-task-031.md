## Design notes and deviations

### ensure_tracking (B2), steps 0–7

- It returns `{"outcome", "process_file", "details"}`. `details` holds
  `collections` and the inspection `rows` (row name, field_id, action,
  reason, extraction name). These are identifiers only, with no PII.
- Steps 0–2 follow the task exactly. In step 0, missing settings count as
  `disabled`. The Process File is read with one `frappe.db.get_value(...,
  as_dict=True)`. If the file does not exist, `DoesNotExistError` is raised,
  and the job catches it.
- Step 3 calls `link_process_file_to_tracking`. If it links, it calls
  `jobs.recompute_client_status` directly (the job is already on the queue)
  and returns `linked_existing`. `link_process_file_to_tracking` and the D9
  transition are unchanged (step 6).
- Step 4 calls `run_fileflo_inspection` unchanged, first for
  `custom_lead_file_collection` and then for `file_collection`, and skips
  empty or equal values. It reuses
  `lifecycle_service._file_collection_candidates_for_process_file`, which
  already has this order and dedupe.
- Step 5 mapping (`outcome_for_rows`), strongest first: `created` →
  `extraction_queued`; reused `Verified` → resolved against the Lead (see
  below); reused `Needs Review` → `needs_review`; other reused →
  `extraction_pending`; `FAILED_RECORD_EXISTS` → `extraction_failed`;
  `ROW_NOT_COMPLETED` → `passport_not_completed`; any other skip reason →
  `passport_no_file`; no rows → `no_passport_row`. Inspection status
  `no_field_ids` or `disabled` → `not_configured`.
- Rows are found only by `field_id` in `passport_field_ids`, through the
  existing inspection. No file-name matching.

**Deviations and additions (all recorded here, none change the listed codes):**

1. **Extra outcome codes.** TASK-035's reason list contains
   `passport_no_file`, `applicant_row_unresolved` and `no_destination`, and
   `ensure_tracking` produces them naturally, so they are in C2. I also added
   three more codes, because otherwise one of the listed codes would be
   wrong for the case:
   - `no_source_lead`: a Verified extraction whose collection has no Lead
     (soft-launch scenario S17).
   - `verified_not_linked`: Verified, nothing blocks creation, but the file
     is still not linked. Example: ADR-014 competing Process Files, or a
     collection mismatch.
   - `inspection_error`: `run_fileflo_inspection` returned `retrying` or
     `failed` (collection missing or a transient error) and gave no rows.

   `ENSURE_OUTCOMES` has 18 codes. TASK-035 can ignore the ones it does not
   need.
2. **Reused Verified extraction.** The task does not cover this case, but
   it is real. An example: the extraction was verified while the Lead had no
   destination, and staff fixed the Lead later. In write mode,
   `ensure_tracking` calls
   `passport_extraction_handlers.handle_verified_extraction` again. This
   path is idempotent, and it has the 3a guard and the flag dedupe. If the
   file is linked afterwards, the result is `linked_existing` and the status
   is recomputed. If not, the read-only `diagnose_tracking_creation` gives the
   reason: `applicant_row_unresolved`, `no_destination`,
   `duplicate_identity_in_lead`, `not_configured`, `disabled`,
   `no_source_lead`, or else `verified_not_linked`. **This is also how
   `duplicate_identity_in_lead` is reported by `ensure_tracking`** (B5). The
   guard itself runs in the asynchronous verification path, so the
   `ensure_tracking` call that queued the extraction cannot see it. The next
   save or Generate sees it.
3. **Priority when rows are mixed.** Failed rows win over not-completed rows,
   and needs_review wins over pending. The task says "only
   FAILED_RECORD_EXISTS" and "only ROW_NOT_COMPLETED" but does not define
   mixed cases. The order follows the task's list order, and a row that
   needs a person comes first.
4. **Extraction statuses `Rejected`, `Duplicate`, `Superseded`.**
   `run_fileflo_inspection` reports these as `reused` (the orchestrator's
   `terminal` action falls into its `else` branch), and Rejected is not in
   `_NON_RETRY_STATUSES`. They are mapped to `needs_review`, because a person
   must act. `extraction_pending` would be wrong for these statuses.
5. **Diagnose mode.** `ensure_tracking(..., diagnose=True)` runs the same
   steps read-only:
   - Step 3 counts active applications with
     `active_applications_for_process_file`. This does not flag.
   - Step 4 uses `_preview_inspection`. This mirrors
     `run_fileflo_inspection` with the same field_id filter, the Completed
     check, `resolve_fileflo_file` and `find_existing_extraction`. It creates
     nothing and enqueues nothing.
   - The Verified case uses `diagnose_tracking_creation` only.

   Tests assert that diagnose mode makes no `run_fileflo_inspection`, link,
   enqueue, `log_error` or recompute call.

### Save trigger (B3)

- `on_update` → `_maybe_enqueue_ensure_tracking(doc)`. It runs after the
  existing link, sync and recompute steps. If the ADR-014 FC-change link
  set the Link during this save, it sees the Link and does nothing. It
  checks, in order: the Link is empty and `workflow_state != "Rejected"`
  (`ensure_service.needs_tracking`), then `is_tracking_enabled()` (cached
  settings). Then it calls
  `frappe.enqueue("the_visaguy.visa_tracking.jobs.ensure_tracking_job",
  queue="short", process_file_name=..., job_id="visa_tracking_ensure::<name>",
  deduplicate=True, enqueue_after_commit=True)`.
- For a primary (`custom_primary_process_file` empty), it also enqueues each
  dependant from `frappe.get_all("PF Process File", filters={"custom_primary_process_file": name})`
  that has no Link and is not Rejected.
  **Deviation:** the task names `get_process_file_family`. That function
  returns only `applicant_name` and `type` (it removes Process File names on
  purpose, for the public payload), so it cannot give job targets. The
  dependant's own Link is used instead. The orchestrator brief allows this
  fallback.
- Fan-out happens only when the saved primary is itself unlinked and
  included. ADR-016 says "must return at once when a link exists". See Open
  questions.
- The whole hook is inside `try/except` → `frappe.log_error`. It never
  raises.
- Frappe v15's `deduplicate` (checked on the bench:
  `frappe/utils/background_jobs.py` line 93) skips the enqueue when a job
  with the same id is `queued` or `started`. Ten saves while the job waits
  therefore give one job. A save while the job is *running* is also dropped.
  This is acceptable, because the job reads current state and the next save
  enqueues again.

### Recompute after linking (B4, task step 7 and section 3)

- `_maybe_link_process_file_for_application` (the path
  `handle_verified_extraction` → `create_tracking_application` uses) now
  calls `enqueue_client_status_recompute(pf)` when
  `link_process_file_to_tracking` reports `linked`. This is a short-queue
  job with `enqueue_after_commit`, `deduplicate=True`, and the same job id
  the save hook already uses
  (`visa-tracking-client-status-recompute::<pf>`), so the two do not stack.
  It is an enqueue and not a direct call. `jobs` imports `lifecycle_service`,
  so a direct call would need a circular import. The hook can also run inside
  a user's Verify request (TASK-033).
- **Addition:** `process_file_handlers._maybe_link_to_tracking` (the
  `after_insert` and FC-change link paths) also enqueues the recompute when
  it links. Without this, a file linked by those paths would keep the Lead
  default status, because the ensure hook then sees the Link and stops. This
  is task step 7 applied to every link path.

### Section 3a guard (B5)

- In `create_tracking_application`, after the reuse check and before the
  destination check: `_duplicate_identity_row` reads the applicant rows of
  **this Lead only**. It skips the resolved row and rows without a Link, and
  compares each linked application's `verification_lookup_hash`. On a match,
  it flags "Visa tracking: same passport on several applicants of one Lead"
  (reference = the Lead) and returns `None`. The same identity on another
  Lead is never seen, so it stays allowed (ADR-015). A row that already
  links an application for the same identity is still reused, which keeps
  redelivery idempotent.
- The hash is computed as before (`_lookup_hash_for_extraction` is the old
  inline code moved into a helper, including its comment).

### Error Log dedupe (B6)

- `_flag_review(title, message, reference_doctype=None, reference_name=None)`.
  Without a reference, the behaviour and the call are unchanged
  (`frappe.log_error(title=, message=)`). With a reference, it looks up
  `Error Log` with `method = title`, the same `reference_doctype` and
  `reference_name`, and `creation > now − 7 days`. If a match exists, it
  writes nothing. Otherwise it calls `frappe.log_error` with the reference.
  In Frappe v15, `Error Log.method` holds the title (checked on the bench).
- References:
  - "applicant row not resolved", "lead has no destination" and "same
    passport…" → the Lead (`Lead` or `CRM Lead`).
  - "competing applications for file collection" → the Process File. This
    one runs on every ensure step 3 of an ambiguous file.
  - "competing process files for file collection" and "applicant passport
    changed" keep the old behaviour, without a reference.
- **Deviation:** the task says "one entry per Process File and reason". The
  two named reasons are raised in `create_tracking_application`, which knows
  the Lead but not the Process File, so they are deduped per Lead and reason.
  A Lead with several applicants that are unresolved for different
  collections gets one entry per 7 days, not one per collection.

### Desk API (B7)

- `generate_visa_tracking(process_file)`:
  1. Role check against `TRACKING_ACTION_ROLES`; otherwise
     `frappe.throw(..., frappe.PermissionError)`.
  2. `frappe.has_permission("PF Process File", "read", process_file, throw=True)`.
  3. The file, plus its dependants when it is a primary.
  4. For each file: `ensure_tracking(name, diagnose=True)`. Unless the outcome
     is `disabled`, `already_linked` or `excluded_state`, it enqueues the real
     run with `enqueue_ensure_tracking` (same job id and dedupe as the hook).

  It returns `[{process_file, outcome, message}]` with the plain-English
  messages from `OUTCOME_MESSAGES`, for example "Passport row is not marked
  Completed." or "Extraction queued. Refresh in a few minutes.". No OCR runs
  in the request.
- `retry_passport_extraction(process_file)`:
  1. The same role and read checks.
  2. It refuses a linked file.
  3. `latest_failed_extraction` reads `Passport Extraction` rows with
     `source_doctype = "FF File Collection"`, source_document in the file's
     collections, and `creation desc` (limit 100). It keeps the newest
     attempt per `(source_document, source_row)` and picks the newest row
     whose latest attempt is `Failed`. A row whose newest attempt is Queued
     or Verified is not retried.
  4. If none is found, it throws "No failed passport extraction to retry for
     this file."
  5. Otherwise it returns
     `frappe.get_attr("passport_extractor.passport_extractor.api.create_retry_extraction")(name)`
     (C1, lazy import).

### Client script (B8)

- New record `PF Process File-visa-tracking-actions` (`dt` PF Process File,
  `view` Form, `enabled` 1, `module` The Visa Guy). The file is valid JSON,
  and each record has name, dt, script and enabled.
- When the doc is saved, `custom_visa_tracking_application` is empty, and
  the user has one of the three roles (`frappe.user.has_role`), it adds two
  buttons in the **Actions** group: **Generate Visa Tracking** (shows a
  msgprint with one line per file) and **Retry passport extraction** (shows
  "Retry queued as {name}…"; server errors are shown by `frappe.call`).
- **Deviation:** Retry is hidden once the file is linked, as Generate is,
  and the server refuses a linked file anyway. Otherwise the server decides
  whether a Failed extraction exists. The client does not query extraction
  status.
- All Client Scripts of a DocType are evaluated in one scope, so the
  identifiers have a prefix (`VT_ACTION_ROLES`, `vt_*`). I checked that the
  two scripts together parse with `node`.
- Note: `Client Script` is not in the `hooks.py` `fixtures` list (TASK-032
  owns it). The existing record also relies on `sync_fixtures` importing
  every file in `fixtures/`. If TASK-032 ever filters Client Script by name,
  it must include both names.

## Open questions

1. **Linked primary with unlinked dependants.** The hook returns at once
   when the saved file is linked (ADR-016), so it does not fan out to
   dependants in that case. They are tracked when they are saved, or through
   Generate on the primary (Generate always lists and enqueues dependants).
   Should a linked primary's save also fan out? That would cost one query per
   save of every linked primary.
2. **Dependant query cost.** `custom_primary_process_file` may not be indexed
   on `tabPF Process File`. The fan-out query runs only on saves of unlinked,
   non-Rejected primaries, but an index would make it cheap.
3. **Dedupe granularity.** "Applicant row not resolved" and "lead has no
   destination" are deduped per Lead and reason, not per Process File (see
   deviations). Is this acceptable?
4. **Mixed-row priority.** When a Failed page and a not-Completed page are
   both present, the result is `extraction_failed`. Should
   `passport_not_completed` win instead?
5. **Missing collection.** A PF whose collection no longer exists makes
   `run_fileflo_inspection` enqueue its own retry chain (up to 3 retries)
   on every ensure run. The result is `inspection_error`. Should
   `ensure_tracking` skip collections that do not exist?
