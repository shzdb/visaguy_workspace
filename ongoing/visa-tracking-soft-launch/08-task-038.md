## Design notes and deviations

### Publish (R1)

- `frappe.publish_realtime("visa_tracking_update", payload,
  doctype=<doctype>, docname=<name>, after_commit=True)`. No `room` and no
  `user` argument. Frappe v15 then uses `doc:<doctype>/<name>`. An open form
  joins this room automatically.
- Frappe queues after-commit events in `frappe.local._realtime_log` and
  removes identical `[event, message, room]` entries. On a rollback it clears
  the queue. So an A2 event from a job that fails and rolls back is not sent.
- `can_publish()` returns False when no site is bound, or during migrate,
  install or patch. This keeps a patch (for example the TASK-036 link patch)
  from queueing thousands of events, and keeps the existing pure tests, which
  have no site, free of publish calls.
- A failure calls `frappe.log_error(title="Visa tracking: realtime alert
  failed")` inside its own `try`. A failure of the log call is ignored. The
  caller never sees an exception.
- Indicators: green for `linked_existing`, `already_linked`,
  `passport_verified`, `application_created`, `status_changed`. Red for
  `extraction_failed`, `unsupported_file_type`, `inspection_error`,
  `no_source_lead` and the three review flags. Orange for all other
  outcomes (queued, pending, needs review, not completed, no file,
  not configured and others).
- **Addition:** three alert-only outcome codes (`passport_verified`,
  `application_created`, `status_changed`). They are in `alert_service`, not
  in `ENSURE_OUTCOMES`, so contract C2 and the coverage report do not change.
  A test checks that they are not in `ENSURE_OUTCOMES`.

### Messages

- A2 and A6 use `OUTCOME_MESSAGES` unchanged, so a toast and the Generate
  dialog say the same thing.
- A3: "Passport needs review.", "Passport extraction failed: <error_code>"
  and "Passport verified.". **Interpretation:** "<reason>" is the
  `error_code` system code (for example `OCR_ENGINE_ERROR`). It is not
  `error_message`, which is free text. When the code is
  `UNSUPPORTED_FILE_TYPE`, the TASK-037 upload message is used. When no code
  is set, the reason is "unknown error".
- A4: "Visa Tracking Application created.". A5: "Client status is now
  <public_title>." (`Visa Tracking Status.public_title`, read with
  `frappe.get_cached_value`, with the status name as a fallback).
- A1 uses the indicator `blue`. The task does not give a colour for A1.

### A1 save toast (R2)

- `_should_announce_ensure` runs before the enqueue. It returns True only
  when all of these are true: `alert_service.in_user_request()`
  (`frappe.local.request` is set and `frappe.local.job` is not), the session
  user has one of `TRACKING_ACTION_ROLES`, and
  `is_job_enqueued("visa_tracking_ensure::<pf>")` is False. The last check
  is the same one that `frappe.enqueue(deduplicate=True)` uses to drop a job.
- A failed check (for example Redis is down) returns False. The enqueue then
  still happens. The toast is never a reason to skip the job.
- Only the saved file gets a toast, not the dependants that the save fans out
  to.
- `msgprint(alert=True)` goes only into the saver's response, so other users
  never see it.

### A2 ensure job (R3)

- The job publishes after `ensure_tracking` returns. `generate_visa_tracking`
  calls `ensure_tracking(diagnose=True)` directly and not through the job, so
  diagnose mode publishes nothing (a test checks this).
- Every outcome is published, also `already_linked` and `disabled`. The
  save hook enqueues only a file that needs tracking, so these occur only in
  a race. The message is correct for the case.

### A3 / A4 / A6 (R4)

- `on_update`: the transition check is now "the status before this save is
  not the same as now". The old check applied only to Verified. For Verified
  the behaviour is unchanged. `Extracted` still goes only to the
  auto-verification path.
- **Deviation (location):** the task names "create_tracking_application /
  link paths". A4/A6 are in `handle_verified_extraction`, which calls
  `create_tracking_application`. Reasons:
  - It has the extraction and the resolved collection, which the room query
    needs.
  - `create_tracking_application` returns only a name or `None`. When the
    result is `None`, `_creation_alert` calls the read-only
    `lifecycle_service.diagnose_tracking_creation` to get the flag. This
    adds a few reads only on the failure path, and only when `can_publish()`
    is True.
  - `lifecycle_service.py` is not changed.
- **Deviation (signature):** `handle_verified_extraction(name, notify=True)`.
  The ensure job passes `notify=False`, because it publishes its own A2
  outcome (for example `linked_existing` or `duplicate_identity_in_lead`).
  Without this, one job run would give two toasts. One line in
  `test_ensure_service.py` changes for this reason.
- A diagnosis result of `disabled`, `not_configured` or `None` publishes
  nothing. Only the three review flags publish.
- Room query: `frappe.get_all("PF Process File", or_filters=[
  ["custom_lead_file_collection", "=", fc], ["file_collection", "=", fc]],
  fields=["name"])`. This is one query. The collection is the
  `source_document` of an `FF File Collection` source, or the collection
  that `_resolve_source_lead` found. A `PF Process File` source publishes to
  that file and needs no query. A `Lead` source publishes nothing.
- A Verified move gives two toasts in order: "Passport verified." (A3), then
  "Visa Tracking Application created." (A4) or the flag (A6). Both come
  after the commit.

### A5 status change (R5)

- `status_service.update_tracking_status` is the only place where a status
  change is committed. Recompute, the process-file-created transition, the
  manual Process File sync, the correction and the reconciliation sweep all
  go through it. The alert is sent only when `previous_status` is not the
  new status. A change of only the message sends nothing.
  `create_tracking_application` writes the first status with
  `append_status_log` and not with this function, so a new application gives
  A4 but no A5.
- The Process File `custom_client_status` is written after this call, in the
  same transaction (`sync_tracking_status_to_process_file`). The publish is
  after the commit, so the reload shows the new value.
- The reconciliation sweep sends one event for each application that it
  repairs. Usually nobody has the form open, so this has no visible effect.

### Client script (R6)

- **Deviation:** the listener is registered in `refresh`, not in `onload`,
  and removed in `on_hide`, not "on unload". Frappe v15 has no form unload
  event. `on_hide` fires when the form page is hidden (checked in
  `frappe/public/js/frappe/form/form.js`). `onload` fires only the first time
  a document opens in the session (`frm.opendocs`), so after a hide the
  listener would not come back. `refresh` runs each time the form shows.
  `vt_listen_for_updates` always calls `frappe.realtime.off` on the previous
  handler first, so each form has exactly one listener.
- The form object is reused for every document of the DocType, so the handler
  reads `frm.doc.name` when the event arrives. It ignores an event whose
  `process_file` (or `tracking_application` on the Application form) is not
  the open document.
- `frappe.show_alert({message: escape_html(message), indicator})`, then
  `frm.reload_doc()` when `!frm.is_dirty()`. A dirty form keeps the user's
  edits and shows only the toast.
- Frappe runs client scripts and the DocType JS with `new Function(...)`, so
  top-level `const` names stay local. The names use the `vt_` and
  `visa_tracking_` prefixes. `node --check` passes on the combined
  PF Process File scripts and on `visa_tracking_application.js`.

### Owner decisions

- Q1: there is no Notification Log, no `sendmail` and no bell. The tests
  check that `new_doc`, `get_doc` and `sendmail` are not called. A source
  scan checks that `alert_service.py` does not contain the DocType name.
- Q2: A1 is shown only for Operations Associate, Operations Team Lead and
  System Manager.
- Q3: A7 is not implemented.

## Open questions

1. **A2 for every outcome.** The job also publishes `already_linked` and
   `disabled` in a race. Should these be silent?
2. **Two toasts on Verified.** A Verified move gives "Passport verified."
   and then "Visa Tracking Application created.". Should A3 Verified be left
   out when A4 follows?
3. **A5 for a manual Process File status edit.** The user who edits
   `custom_client_status` also gets the "Client status is now …" toast, and
   the form reloads (it was just saved, so it is not dirty). This is
   harmless. Should manual edits be silent?
4. **Failed reason text.** The toast shows the `error_code` (for example
   `OCR_ENGINE_ERROR`). Should known codes have plain-English texts?
