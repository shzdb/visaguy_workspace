## Design notes and deviations

### One mapping for the service and the report

The report already uses `ensure_service.outcome_for_rows`. So the refinement
is in the pure row mapping, not in a separate step after it:

- A row with `reason = FAILED_RECORD_EXISTS` and
  `error_code = UNSUPPORTED_FILE_TYPE` maps to `unsupported_file_type`.
  Every other failed row maps to `extraction_failed` as before.
- `unsupported_file_type` comes directly before `extraction_failed` in the
  priority. So a file that would have been `extraction_failed` becomes
  `unsupported_file_type` if at least one failed row has the code (task item
  2: "a failed passport row"). Stronger outcomes (`extraction_queued`,
  Verified, `needs_review`, `extraction_pending`) still win, as
  `extraction_failed` did.
- Each caller fills `error_code` on its failed rows. `ensure_tracking` uses
  one query (below). The report reads it from the extraction record it
  already loaded for the row.

### The one query in ensure_tracking (H2)

`run_fileflo_inspection` (not in my ownership) and `_preview_inspection` do
not put the extraction name on a failed row. So `_latest_failure_codes` reads
the codes with one `frappe.get_all` for all failed rows of the file:

- filters: `source_doctype = "FF File Collection"`, `source_row in <failed row
  names>`, `status = "Failed"`;
- fields: `source_row`, `error_code`; `order_by = "creation desc"`;
- the newest record per row decides.

The query runs only when at least one row is failed. It is the same in normal
and diagnose mode, because both give the same row shape. FF File Collection
File row names are unique, so `source_row` alone identifies the row.

**Interpretation:** the query takes the newest *Failed* extraction of the
row, and does not also match `passport_file`. A row is "failed" only when
`find_existing_extraction` found a Failed record for the current file. That
record is the newest for the row, unless an older file of the same row has a
newer failure. That case is not realistic: a new upload gets a new extraction.

### Desk (H3)

- The message is the exact task text. `generate_visa_tracking` needs no
  change: it looks up `OUTCOME_MESSAGES[outcome]`.
- `retry_passport_extraction`: the existing single query in
  `latest_failed_extraction` now also reads `error_code`. If the chosen
  record has `UNSUPPORTED_FILE_TYPE`, the function throws the same message and
  does not call C1. It uses no extra query.
- **Deviation (small):** `latest_failed_extraction(pf)` now returns the record
  dict (`name, status, source_document, source_row, error_code`), not only the
  name. It has no other caller in the repository (checked with grep).
- **Interpretation:** item 4 says "the latest failed extraction". Retry picks
  one record: the newest row whose latest attempt is Failed. If that record
  is unsupported, Retry refuses, even if an older row of the same file failed
  for another reason. This follows the task text. See Open questions.

### Report (H4)

- `error_code` is added to the existing Passport Extraction query. There is
  still one query per batch of collections, and no query per row.
  `test_query_count_does_not_grow_with_files` still passes.
- The Next Step text comes from `OUTCOME_MESSAGES` through `REASON_MESSAGES`.
  The report does not override it.
- The summary counts `unsupported_file_type` after `extraction_failed`,
  because the summary follows the order of `ENSURE_OUTCOMES`.
- `error_code` is a system code, not a passport value.
  `test_no_passport_values_are_read_or_shown` still passes.

### Contract C2

The new code is in `ENSURE_OUTCOMES`, directly after `extraction_failed`. This
changes the position of the later codes in the tuple. The known consumers
(report summary order, and the tests that check membership and uniqueness)
do not depend on position.
