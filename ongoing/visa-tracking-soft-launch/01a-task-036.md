## Design notes and deviations

### Patch structure

- `MATCHED_NAMES` is one `frozenset` constant:
  `passport`, `passport copy`, `passport1`, `passport2`, `passport جواز سفر`.
- `normalize_file_name()` is pure: replace U+00A0 with a space, trim,
  lower-case, merge whitespace (`\s+` to one space), remove one trailing
  `" - <digits>"`. `is_primary_passport_name()` compares the result with
  `MATCHED_NAMES`. `chunked()` yields lists of at most 1000 items.
- Order in `execute()`: read candidate rows and build the counts; ensure
  `FF Field ID` `passport`; update template rows; update collection rows;
  print. Everything runs in the patch runner's transaction; the patch runner
  commits. The patch itself does not call `frappe.db.commit`.
- Candidate rows are read with `frappe.get_all(..., filters={"file_name":
  ["like", "%passport%"]}, limit_page_length=0)` and explicit fields
  (`name, file_name, field_id`, plus `status, document` for collection rows).
  Every matched name contains `passport`, so no matched row is missed. The
  match itself is done in Python on the normalized name.
- The `UPDATE` table name comes from a module constant, never from input.
  Values go through `%(field_id)s` and `%(names)s` (tuple).
- `execute()` and `dry_run()` return the counts as a dict (without row
  names), so `bench execute` also shows them.
- The patch prints one line and returns when the FileFlo tables
  (`FF Field ID`, `FF File Template File`, `FF File Collection File`) do not
  exist. This keeps `bench migrate` safe on a site without FileFlo.
- `patches/v1_0/` has no `__init__.py`. `patches/` has none either; both are
  namespace packages. The module path imports on the bench python
  (`the_visaguy.patches.v1_0.set_passport_field_id`, `execute` and `dry_run`
  callable).

### Deviations and choices not fixed by the contract

1. **Unmatched-name report has a privacy floor.** The contract asks for the
   top 20 unmatched names that contain `passport`. The report lists
   normalized labels (with the ` - N` suffix removed), sorted by row count,
   capped at 20, each cut to 60 characters. Labels that occur in fewer than
   3 rows, and labels that end like a file name (`.pdf`, `.jpg`, ...), are
   not listed; only their number is printed ("held back"). Reason: the
   constraint "do not log file URLs or names of people". A label that occurs
   once or twice can be a person's name or an uploaded file name; a template
   label occurs many times. The owner can lower `UNMATCHED_MIN_ROWS` if the
   held-back count is large.
2. **"updated" in the count block.** In `dry_run()` it is the number of
   matched rows with an empty `field_id` (rows that `execute()` would
   update). In `execute()` it is the number of rows sent to `UPDATE`. If a
   user sets a `field_id` between the read and the `UPDATE`, the SQL guard
   skips that row, so the real number can be lower. It cannot be higher.
3. **Whitespace-only `field_id` counts as empty.** This matches the SQL
   guard `IFNULL(field_id, '') = ''`, which is true for spaces under
   MariaDB's PAD SPACE collations.
4. **Guards also refuse `limit <= 0`.** In Frappe, `limit_page_length=0`
   means "no limit", so `limit=0` would scan the whole site. The guard
   normalizes `limit` with `max(int(limit or 0), 0)` and refuses when
   `collections is None and not limit`. `collections=[]` returns `[]` with
   no query and no log line. The guard runs before the settings checks, so
   the refusal is always logged.
5. **Log line.** The guards use `frappe.logger().warning(...)`, as
   `fileflo_inspection_service` does. No Error Log is written.
6. **Status buckets** in the report: `Completed`, `Uploaded`, `Rejected`,
   `blank`, `other` (in that print order).

### FileFlo row creation (validation item "a new collection gets the field ID")

Read from code on the bench (not run):

- `fileflo/fileflo/document_fetch.py::document_fetch` copies every field
  that exists on both `FF File Template File` and `FF File Collection File`,
  so `field_id` and `field_id_link` are copied. Lead collections use it:
  `visaguy_crm/file_collection_from_lead.py:167` and
  `visaguy_crm/allocated_to_process_file.py:442`.
- Multi-file uploads copy `field_id` to the extra rows and name them
  `"<name> - N"`: `fileflo/fileflo/data_collection.py:204`,
  `visaguy_crm/visaguy_crm/data_collecting_form.py:242` and `:273`.
- `processflo/processflo/generate_file_collection.py::generate_file_collection_process_file`
  (line 87) copies only `file_name, group_name, mandatory, multiple,
  max_allowed, format`. It does **not** copy `field_id`. ADR-016 says the
  primary passport row lives in the Lead collection, so this path may not
  matter, but a Process-File-stage collection made through it will have no
  `field_id`. See Open questions. No change was made (no change to
  `processflo` is in scope).

   in `processflo` does not copy `field_id` from the template. Is any
   primary passport row created through this path (Process File
   collections), or only through `document_fetch` (Lead collections)? If the

   patch sets `field_id_link` to `passport` even if `field_id_link` already
   holds another value. The contract guards on `field_id` only. Should such
   rows be skipped and counted instead?

   deviation 1)?
