## 2. The five-failure triage

Five failures/errors surfaced on today's first full run. **None of the five was a new application defect.** Each was triaged to one of two categories and fixed; each fix was mutation-proven (reverting it makes the corresponding new/repaired test fail).

### 2a. Two stale-contract failures (CORS)

Two tests asserted the **pre-ADR-008** CORS contract: that
`response_service.to_http_response` itself sets
`Access-Control-Allow-Origin`. ADR-008 (2026-08, already accepted) removed
that emission — Frappe became the sole emitter, with origin authorisation
retained in the request path via `security.validate_cors(origin)` instead of
the response header. That change shipped inside commit `8254f93` with no
accompanying test update, so these two tests kept asserting the old contract
and had been silently red (or skipped/stale) since.

Fix: rewrote both tests to the ADR-008 contract — asserting the request-path
origin check rather than a response header the app no longer sets.
Mutation-proof: removing the `validate_cors` call from the request path
(simulating a regression back toward the pre-ADR-008 gap ADR-008 fixed) makes
both tests fail.

### 2b. Three test-isolation failures, not defects

The test site is **persistent** and does not roll back between runs (this is
a known, accepted property of `visa-tracker-test.localhost`, not a bug in the
site). Two consequences collided in these three failures:

- `tabVisa Tracking Application` still held `VTA-2026-00041`, created
  **2026-07-22 20:12**, with `application_closed=0` — a leftover from a prior
  session, six weeks old.
- The audit table (`Visa Tracker Audit Log`) held **37 rows**, accumulated
  across every prior run against this site, against a test that asserted
  exactly `2`.

Root cause tying both together: every test in the suite used the same
hardcoded synthetic identity, `P0000000` / `1990-01-01`. Application logic
(`lifecycle_service.create_tracking_application`) **correctly** enforces "one
active application per identity," so a fresh test run using that same
identity legitimately reused the six-week-old row instead of creating a new
one — the application behaved exactly as designed; the test suite's fixture
strategy was the bug.

Fix: gave the affected tests unique synthetic identities (not reused across
the suite), scoped their assertions to records they themselves created rather
than global table state, and added `tearDown` cleanup. Mutation-proof:
temporarily reverting the identity-uniqueness fix reproduces the original
collision and the original assertion failure.

**This specific instance is fixed. The rest of the suite has not been swept
for the same unscoped-assertion pattern — see TASK-015, created this
session, for that follow-up.**

Two mutations worth recording, since they characterise real regression risk
on this code path rather than being incidental to test-writing:

- Replacing the controller's ORM `doc.save()` with `frappe.db.set_value()` in
  the auto-promotion path leaves `verified_by` empty. This is exactly the
  failure mode ADR-007's own "Decision" section warns about — the ORM save
  exists specifically so the controller's `_preserve_verification_audit`
  stamp fires, and skipping it would silently break the *next* save of that
  document, not the one under test.
- Removing the job's re-check of current status before promoting — the
  re-check ADR-007 calls out as "the behaviour most likely to regress" —
  makes the already-Rejected-record case raise `ValidationError` on an
  illegal transition, instead of the contract's required silent no-op.

## 4. TASK-012 — rate-limit enumeration hardening

**Status: implemented per the owner's 2026-09-01 decision (ADR-009), runtime-proven on the test site, uncommitted, not deployed.**

### Implementation, matching the spec exactly

- `build_client_scope_key(origin_scope, source_ip)` added to
  `rate_limit_service.py` — same keyed-HMAC construction as the existing
  `build_client_key`, target bucket omitted, own cache-key prefix
  (`visa_tracker:failed_scope:` vs. the existing `visa_tracker:failed:`) so
  it can never collide with the per-identity key.
- Two new `Visa Tracker Settings` Int fields:
  `scope_maximum_failed_attempts` (default 20),
  `scope_lockout_minutes` (default 60), clamped MIN/MAX the same way as the
  existing per-identity fields, with fallback defaults in
  `visa_tracking/utils/constants.py`.
- `verification.py` consults both counters, refuses on either, sets
  `Retry-After` to the greater of the two, and increments both only on the
  `not_found` branch — not on CORS rejection, malformed body, or the
  feature-disabled path.
- The generic failure response body remains byte-identical (verified by md5)
  across every reachable failure mode; only `Retry-After` varies.

### Live-HTTP proof (the validation that matters most for this task)

Mirroring the method of `09j-live-wire-contract-smoke.md` Appendix C:
werkzeug served on a loopback port from the bench `sites` directory, `curl`
with an explicit `Host: visa-tracker-test.localhost` header, against real
Redis.

- **The exact regression this task exists to fix:** the same passport number
  with an incrementing DOB, previously 0/7 (never locked out), now returns
  `Retry-After: 3597` at attempt 21.
- **Existing behaviour unchanged:** an identical wrong pair still locks out
  at attempt 6, `Retry-After: 900` — the pre-existing per-identity control is
  untouched by this change.
- Response body md5 identical across `not_found`, both rate-limited paths
  (per-identity trip, per-IP-scope trip), and CORS rejection.

Full `the_visaguy` suite after this work: **298 green** (see §1).

### A real secondary bug, found and fixed, worth recording for recurrence

Adding an `Int` column to an **already-installed** Frappe Single DocType
means a record saved before that column existed reads the new column back as
`0`, not `None`. The pre-existing guard in `validate_public_tracking_bounds`
(`if value is None: continue`) let that `0` reach the bound-check logic for
the two new fields and throw "must be between 1 and 100" on **every** save
of `Visa Tracker Settings` — breaking 14 unrelated tests that saved the
settings Single as part of their own setup, not anything related to rate
limiting.

Fix: treat falsy as "unset -> use default" for `scope_maximum_failed_attempts`
and `scope_lockout_minutes` **only**; every pre-existing field keeps its
strict `is None` semantics unchanged. Since both new bounds start at 1, `0`
was never a legal configured value for either field, so nothing was loosened
by this change — it only stopped a false-positive validation error.

**This will recur** on the next Int/Check field added to an already-installed
Single anywhere in this codebase, unless the same falsy-vs-None distinction
is made deliberately each time. Worth a mental note for future schema
changes to `Visa Tracker Settings` or any other long-lived Single.

See TASK-012's own "Completion evidence (2026-09-01)" section and ADR-009 for
the full decision record.

## 6. New finding: raw traceback on non-JSON body (risk 24, TASK-014)

While probing `verify_identity`'s constant-response property with malformed
inputs during TASK-012's live-HTTP testing, a **pre-existing, unrelated**
finding surfaced: a genuinely non-JSON request body is intercepted by
Frappe's own `make_form_dict` before the app's handler ever runs, and returns
a raw traceback page on a public, unauthenticated endpoint. By contrast, a
valid-JSON-but-wrong-shape body (e.g. `[]`) is handled correctly by the app's
own `UnsafeRequestError` path and returns the byte-identical generic body.

This is honestly **not a defect in `verification.py`** — the failure happens
in Frappe core before the whitelisted method is ever entered, so a fix inside
the method cannot help. Recorded as risk 24 and TASK-014, with the
investigation framed as open (middleware/early-intercept vs. web-server-layer
handling vs. an upstream Frappe fix) rather than prescribing a solution that
hasn't been evaluated.
