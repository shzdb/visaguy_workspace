- REQUIRED FIX POLICY: preserve the guard's legitimate original intent — tolerating the pre-install / pre-migrate state where the DocType does not exist yet — while working correctly for a Single. Use a DocType-existence check (e.g. `frappe.db.exists("DocType", SETTINGS_DOCNAME)`) and/or rely on the existing `frappe.DoesNotExistError` handler, rather than a table check. Do NOT simply delete the guard without preserving install-time safety; `frappe.flags.in_install` is already handled by the caller and must keep working.

D2 — `enqueue_passport_extraction` raises on every "created" extraction.
- File: `the_visaguy/visa_tracking/services/extraction_orchestrator.py`, ~lines 85-91.
- Code calls `job = frappe.enqueue(..., enqueue_after_commit=True)` then `pex.db_set("last_job_id", job.id)`.
- Frappe v15 `frappe/utils/background_jobs.py`: the `enqueue_after_commit` branch does `frappe.db.after_commit.add(enqueue_call)` then a bare `return` — it returns `None`. So `job.id` raises `AttributeError`. Coordinator read this source directly; it is definitive.
- REQUIRED FIX POLICY: keep the after-commit safety semantics (the job must NOT be enqueued before the transaction commits, or a worker can pick up a record that does not exist yet). The preferred fix is to generate the job id ourselves, pass it to `frappe.enqueue(job_id=...)`, keep `enqueue_after_commit=True`, and record that same id via `db_set("last_job_id", ...)`. Verify Frappe's `job_id` parameter semantics in the installed source before relying on them. If that proves unworkable, the fallback is to stop recording `last_job_id` and document why — but do NOT "fix" this by dropping `enqueue_after_commit`, which would reintroduce the race. Whatever you choose, the function's return value must stay coherent for its callers — check every call site.
