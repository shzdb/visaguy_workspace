## 1. The test-site rebuild and its two documented configuration deltas

The site `visa-tracker-test.localhost` was dropped and rebuilt from scratch
on 2026-09-01 (see `docs/operations/visa-tracking-runbook.md`, "Test site
rebuild" — already corrected by hand this session and not touched by this
report). Two `Visa Tracker Settings` values on the rebuilt site
deliberately differ from `visaguy` and are documented in the runbook as such:

| Field | Test-site value | `visaguy` value | Why it differs |
|---|---|---|---|
| `frontend_base_url` / `support_link` | `https://tracker-test.example.com` (and `/support`) | `http://localhost:5173/` | The test site needs a stable, asserted-against value (`test_cors_against_live_settings`, `test_status_payload_against_live_documents`) rather than a dev-server URL that would break as soon as the value were copied literally. |
| `passport_field_ids` | `passport_front` / `passport_back` (newline-separated) | `passport` | The test fixtures exercise two-sided passport capture (front/back), which `visaguy`'s single `passport` field ID does not need to distinguish. This value was undocumented before this session and had to be recovered from a test fixture comment — now recorded in the runbook. |

Both values are inert on `visaguy` itself — they only affect what the test
site asserts against — but a future agent copying test-site config to
production, or vice versa, would silently break CORS or the FileFlo
inspection path. This is why they are called out explicitly rather than left
implicit in fixture code.

## 2. The missing-`visaguy_crm`/`hrms` discovery

The rebuilt site initially installed only `the_visaguy`, `fileflo`, and
`passport_extractor` — not `visaguy_crm` or `hrms`. This looked adequate at
first: `the_visaguy`'s own suite ran green against it. It was not adequate.

**What it hid:** `visaguy_crm` owns the customisations that make
`PF Process File` and `Lead` behave like production —
`workflow_state` (a Link to `Workflow State`, driven by the active
`Process File Workflow`), `custom_form_submitted`, and the mandatory
`custom_department` / `process_` chain. Without `visaguy_crm` installed,
TASK-016's own resolver input field — `workflow_state` as a real,
workflow-governed Link — did not exist on the test site at all. TASK-016 was
initially validated against a hand-created plain `Select` field standing in
for it, which is not the same contract as the production Link/Workflow
field and would not have caught a workflow-state-transition bug the real
field could surface.

**Why `hrms` had to come with it:** `visaguy_crm`'s `Company` customisation
references `Salary Component`, which only exists once `hrms` is installed.
Installing `visaguy_crm` alone aborts partway through its own install
migration, leaving its hooks active (so Lead/Process File save behaviour
changes) but some of its fields missing (so the schema is inconsistent) —
worse than not installing it at all. Both apps had to be installed together.

**What installing both broke:** 28 previously-green tests went red, with a
single root cause: fixtures across the suite were building `PF Process File`
and `Lead` documents directly, skipping fields that only became mandatory
once `visaguy_crm`'s validation was actually active. The real mandatory
chain, walked end to end:

```
custom_department -> Department.company -> Company.{currency, country, abbr, gst_category}
                                          -> Lead.{mobile_no, custom_zone, custom_lead_source, custom_destination}
                                          -> Customer.naming_series (via Zone)
```

None of this chain is optional in production — every real Lead and Process
File satisfies it, because `visaguy_crm`'s validation has always run against
them there. The test fixtures had simply never been exercised against that
validation before, because the app that enforces it was not installed.

**Fix, not a workaround:** a shared
`the_visaguy/the_visaguy/visa_tracking/tests/fixtures.py` was written, with
`make_process_file()` / `make_lead()` helpers that get-or-create synthetic
records satisfying the full chain above. No assertion anywhere in the 28
affected tests was weakened, relaxed, or skipped — the tests now build
documents that could actually exist in production, and assert the same
things they always did.

**A related divergence found during the same pass:** `CRM Migration
Settings` exists on `visaguy` but is not installed by any app on the
rebuilt test site. Creating a `Lead` as a user holding the "Consultant Role"
therefore hits `visaguy_crm`'s auto-assign path, which expects that
doctype's configuration and fails without it. `fixtures.py` works around
this by inserting Leads as an unprivileged user rather than attempting to
replicate `CRM Migration Settings` on the test site — replicating it was
judged out of scope for a test-fixture fix and is not required for TASK-016
to be valid.

**This is now risk 27** in `docs/risks-and-open-questions.md`: a rebuilt
test site missing `visaguy_crm`/`hrms` produces a green suite that does not
reflect production, because the constraints those apps enforce are not
present to fail against. The runbook's rebuild recipe (already corrected by
hand ahead of this session) is the documented mitigation going forward.

**A second, independent finding surfaced in the same investigation:**
`visaguy_crm`'s Lead hooks call `frappe.db.commit()` mid-transaction on
every Lead save — confirmed while tracing why some test rows created and
deleted mid-test were surviving between runs, the same leaked-state pattern
already described in
`ongoing/visa-tracking-implementation/12-session-2026-09-01-task-011-012.md`
§2b. This is now risk 26, with TASK-018 created to investigate and remove
the unconditional commit. It is a real production atomicity concern
(a later failure in the same request can no longer be rolled back past that
commit point), not only a test nuisance.

## 3. TASK-016 delivery

**Status: implemented, green, mutation-proven. Uncommitted.**

- `resolve_client_status()` — pure function,
  `the_visaguy/the_visaguy/visa_tracking/status_resolution.py`. Full mapping
  table, forward-only ladder guard, ON_HOLD exemption in both directions,
  and a hard Rejected guard checked first and independent of the mapping
  table's mere omission of `Rejected`.
- Thin, enqueue-only `on_update` trigger on `PF Process File`, firing only
  when `workflow_state` or `custom_form_submitted` actually changed on that
  save (compared against the pre-save document) — never on every save, so a
  manual ops override is not silently overwritten within seconds of being
  set.
- `recompute_client_status` queued job, re-reading current state at
  execution time rather than acting on data captured at enqueue time.
- `run_client_status_reconciliation_sweep`, wired to an hourly scheduler
  entry in `hooks.py`, and `repair_client_status_drift` in
  `reconciliation_service.py` — both routed through the same resolver as the
  job, so the sweep repairs drift instead of only reporting it.
- The six replacement `Visa Tracking Status` records.
- `public_title` on `Visa Tracking Status`; `title` wired into the public
  API payload, both on the current-status object and on each timeline
  entry (see exact shape below).
- `PF Process File.custom_client_status` set `read_only: 1`.

### Exact public payload shape (for TASK-017)

Top-level `data`:
`applicant_name_masked, passport_number_masked, destination, visa_type,
current_status, title, public_message, last_updated, timeline, support_link`
— `title` new, immediately after `current_status`.

Each `timeline` entry:
`status, title, message, effective_on, icon` — `title` new, immediately
after `status`.

`title` is always a string, never null, in both places. The generic-failure
response body is unchanged and byte-identical across every failure mode.

Full detail recorded in TASK-016's own "Completion evidence (2026-09-02)"
section.
