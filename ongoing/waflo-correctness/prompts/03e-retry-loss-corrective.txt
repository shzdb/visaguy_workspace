THE DEFECT (message loss — this is the whole point of this task):

`send_whatsapp_template` now returns `None` when it defers a rate-limited send, after creating
a pending `WhatsApp Message` record via `log_pending_retry_whatsapp_message`. That record
deliberately has NO `message_id`.

`waflo/waflo/messaging/retry_message.py` does:

    message_id = send_whatsapp_template(..., rate_limit=True)
    message = frappe.db.get_value("WhatsApp Message", {"message_id": message_id}, "name")
    message_doc = frappe.get_doc("WhatsApp Message", message)
    initail_message = frappe.get_doc("WhatsApp Message", doc["name"])
    initail_message.custom_retried_message = message
    initail_message.save()

When the retry is ITSELF rate limited, `message_id` is `None`. The filter
`{"message_id": None}` then matches records whose message_id is NULL — and pending retry
records are exactly that. So it selects an ARBITRARY UNRELATED RECORD, and then sets
`custom_retried_message` on the original.

`schedule_retry_message` filters on `{"custom_should_retry": 1, "custom_retried_message": None}`.
Once `custom_retried_message` is set, the original is excluded FOREVER. The message is
silently lost. This directly violates the never-drop requirement.
